# ၃ · IS-IS

IS-IS သည် OSPF နှင့် တူညီသော လုပ်ဆောင်ချက်ကို လုပ်ဆောင်ပေးပြီး Dijkstra SPF algorithm အတူတူပင် အသုံးပြုသည်။ ကွဲပြားသောအချက်မှာ ဒီဇိုင်းရေးဆွဲမှုဆိုင်ရာ ဒဿန (design philosophy) ဖြစ်သည် — ထိုကွာခြားချက်များကြောင့်ပင် ကမ္ဘာ့အကြီးဆုံး Service Provider ကြီးများက ၎င်းကို ဆက်လက်ရွေးချယ် အသုံးပြုနေကြခြင်း ဖြစ်သည်။

!!! note "ဤစာမျက်နှာတွင် Syntax သာ ဖော်ပြထားပြီး Live output များကို Lab တွင် လေ့လာပါမည်"
    ဤစာမျက်နှာတွင် **syntax များနှင့် အခြေခံသဘောတရားများကိုသာ** ဖော်ပြထားပြီး လုပ်ကြံဖန်တီးထားသော command output များကို ထည့်သွင်းမထားပါ။

    IS-IS ကို live equipment များပေါ်တွင် စမ်းသပ်ထားပြီးဖြစ်သည်- **[Phase 1 · Lab 02](../01-bgp/lab-02-isis-underlay.md)** တွင် လက်တွေ့လည်ပတ်နေသော BGP deployment တစ်ခုကို OSPF မှ IS-IS သို့ ပြောင်းလဲအသုံးပြုပုံနှင့် စစ်မှန်သော adjacency၊ database နှင့် route output များကို ဖမ်းယူပြသထားပါသည်။

## လူတိုင်း အံ့အားသင့်ရသည့် ပထမဆုံးအချက်

**IS-IS သည် IP ပေါ်တွင် မ run ပါ။** ၎င်းသည် Layer 2 ပေါ်တွင် မိမိကိုယ်ပိုင် protocol အဖြစ် တိုက်ရိုက် run သည်။

OSPF သည် IP packet များအတွင်း (Protocol 89 အဖြစ်) ထည့်သွင်း သယ်ဆောင်သွားခြင်း ဖြစ်သည်။ IS-IS မှာမူ မည်သည့်အရာ၏ အတွင်း၌မျှ ရှိမနေပါ — ၎င်းသည် IP ၏ ခရီးသည်မဟုတ်ဘဲ IP နှင့် ရင်ပေါင်တန်းနေသော ရဲဘော် (peer of IP) ဖြစ်သည်။

ယင်းကြောင့် အောက်ပါလက်တွေ့အကျိုးရလဒ် ၂ ခု ဖြစ်ပေါ်လာသည် -

- **အဝေးမှနေ၍ လှမ်းတိုက်ခိုက်ရန် အလွန်ခက်ခဲခြင်း (Much harder to attack remotely)။** Internet ဖြတ်သန်း၍ IS-IS process ထံသို့ packet တစ်ခု လှမ်းပို့၍ မရနိုင်ပါ၊ အကြောင်းမှာ လမ်းကြောင်းရှာဖွေပေးမည့် IP header မပါရှိသောကြောင့် ဖြစ်သည်။ တိုက်ခိုက်သူသည် ထို physical link ပေါ်သို့ တိုက်ရိုက် ရောက်ရှိနေမှသာ တိုက်ခိုက်နိုင်မည် ဖြစ်သည်။
- **မိမိတည်ဆောက်နေသော အရာအပေါ် ပြန်လည်မှီခိုမှု မရှိခြင်း။** IS-IS သည် IP ချိတ်ဆက်နိုင်စွမ်း (IP reachability) ကို တည်ဆောက်ရန်အတွက် IP ကို ပြန်လည်အသုံးပြုရသည့် ရှုပ်ထွေးလှည့်ပတ်သော သဘောတရား (circularity) လုံးဝ မရှိပေ။

ဤသည်မှာ အမှန်တကယ် ခိုင်မာသော လုံခြုံရေးနှင့် ကြံ့ခိုင်မှုဆိုင်ရာ အားသာချက်ဖြစ်ပြီး Provider များက ၎င်းတို့၏ backbone network များအတွက် IS-IS ကို နှစ်သက်ရသည့် အကြောင်းရင်းတစ်ခု ဖြစ်သည်။

## Addressing စနစ်- NET

IS-IS သည် IP အတွက် အသုံးမပြုမီကတည်းက စတင်ပေါ်ပေါက်ခဲ့ခြင်း ဖြစ်သည်။ ၎င်းသည် OSI protocol suite မှ ဆင်းသက်လာခဲ့ပြီး router များကို OSI-style addressing စနစ်ဖြစ်သည့် **NET** (Network Entity Title) ဖြင့် ယနေ့တိုင် သတ်မှတ်ဖော်ပြဆဲ ဖြစ်သည်။

```
router isis CORE
 net 49.0001.0000.0000.0001.00
```

အစိတ်အပိုင်းတစ်ခုချင်းစီကို ခွဲခြမ်းကြည့်ပါက -

| အစိတ်အပိုင်း (Part) | တန်ဖိုး (Value) | အဓိပ္ပာယ် (Meaning) |
|---|---|---|
| AFI | `49` | Private addressing — RFC 1918 နှင့် သဘောတရားတူညီသည် |
| Area ID | `0001` | ဤ **router** မည်သည့် area တွင် ပါဝင်သည်ကို ပြသည် |
| System ID | `0000.0000.0001` | ထူးခြားသော သီးသန့် router identifier ဖြစ်ပြီး 6 bytes ရှိသည် |
| NSEL | `00` | Router တစ်ခုအတွက် အမြဲတမ်း `00` ဖြစ်သည် |

လူအများ မှားယွင်းတတ်သော လက်တွေ့ကျသည့် မှတ်ချက် ၂ ခု -

- **System ID သည် domain တစ်ခုလုံးတွင် ထူးခြားသီးသန့် (unique) ဖြစ်ရပါမည်**၊ ထို့အပြင် တိတိကျကျ 6 bytes ရှိရမည်။ အများသုံး အလေ့အထအရ loopback address ကို အခြေခံ၍ သတ်မှတ်ကြသည်- ဥပမာ `1.1.1.1` ကို octet တစ်ခုစီတွင် ဂဏန်းသုံးလုံးပြည့်အောင် ဖြည့်စွက်ကာ `0010.0100.1001` ဟု ရေးသားကြသည်။
- **Area သည် Router ၏ ဂုဏ်သတ္တိဖြစ်ပြီး Interface ၏ ဂုဏ်သတ္တိ မဟုတ်ပါ။** ၎င်းသည် OSPF နှင့် လုံးဝဆန့်ကျင်ဘက်ဖြစ်ပြီး IS-IS router တစ်ခုသည် မတူညီသော area နှစ်ခုထဲတွင် interfaces များ ခွဲခြားပါဝင်ခွင့် မရှိပါ။

## Area များအစား Level များကို အသုံးပြုခြင်း

IS-IS တွင် အဆင့် ၂ ဆင့်သာရှိသော hierarchy ဖွဲ့စည်းပုံ ပါဝင်သည် -

| Level | အခန်းကဏ္ဍ (Role) | OSPF ၏ တူညီသောသဘောတရား |
|---|---|---|
| **L1** | Intra-area — မိမိ area အကြောင်းကိုသာ အသေးစိတ် သိရှိသည် | Non-backbone area |
| **L2** | Inter-area — Backbone အဖြစ် ဖွဲ့စည်းထားသည် | Area 0 |
| **L1/L2** | နှစ်မျိုးစလုံး — Area နှစ်ခုကြားရှိ နယ်စပ် router | ABR |

အလွန်အရေးပါသော ဖွဲ့စည်းပုံဆိုင်ရာ ကွာခြားချက်မှာ- **L2 backbone သည် နံပါတ်တပ်ထားသော area တစ်ခု မဟုတ်ဘဲ အချင်းချင်း အဆက်မပြတ် ဆက်စပ်နေသော L2 router များ၏ ချိတ်ဆက်မှုကွင်းဆက် (contiguous chain) သာ ဖြစ်သည်။** ၎င်းသည် "area 0" ဖြစ်ရန် မလိုပါ — အချင်းချင်း ချိတ်ဆက်မိနေရန်သာ လိုအပ်သည်။

ထိုပြောင်းလွယ်ပြင်လွယ်မှုသည် အလွန်အဖိုးတန်ပါသည်။ OSPF backbone ကို တိုးချဲ့လိုပါက area 0 ကို တိုးချဲ့ရမည်ဖြစ်ပြီး topology က အဆင်မပြေပါက virtual links များကို အသုံးပြုရတတ်သည်။ IS-IS backbone ကို တိုးချဲ့ရန်အတွက်မူ router အချို့တွင် L2 ကို enable လုပ်ပေးလိုက်ရုံသာ ဖြစ်သည်။ ကုမ္ပဏီတစ်ခုနှင့်တစ်ခု ပေါင်းစည်းဝယ်ယူမှုများဖြင့် ကြီးထွားလာသော Provider များအတွက် ဤအချက်က ခေါင်းခဲမှုကို များစွာ သက်သာစေသည်။

L1 router တစ်ခုသည် မိမိ area ပြင်ပသို့ ဆက်သွယ်လိုပါက အနီးဆုံးရှိ L1/L2 router ထံသို့ traffic ပို့ပေးရပြီး၊ ထို L1/L2 router က မိမိကိုယ်ကို ထွက်ပေါက်အဖြစ် ကြေညာထားသည့် bit တစ်ခုကို သတ်မှတ်ပြသထားသည်။ L1 router အနေဖြင့် ပြင်ပတွင် မည်သည့်အရာများ ရှိနေသည်ကို သိရန်မလိုဘဲ — မည်သူ့ထံ လက်ဆင့်ကမ်းရမည်ကိုသာ သိရှိရန် လိုအပ်သည်။

## TLVs: IS-IS သည် အဘယ်ကြောင့် ယနေ့တိုင် အသုံးဝင်နေဆဲဖြစ်သနည်း

IS-IS သည် အချက်အလက်အားလုံးကို **TLVs** — Type, Length, Value ပုံစံဖြင့် encode ပြုလုပ် သိမ်းဆည်းသည်။ Router တစ်ခုသည် မိမိနားမလည်သော TLV type တစ်ခုနှင့် တွေ့ကြုံပါက length field ကို အသုံးပြု၍ ၎င်းကို သပ်သပ်ရပ်ရပ် ကျော်ခွသွားပြီး ပုံမှန်အတိုင်း ဆက်လက် အလုပ်လုပ်နိုင်သည်။

၎င်းသည် encoding ဆိုင်ရာ သေးငယ်သော အသေးစိတ်အချက်တစ်ခုဟု ထင်ရနိုင်သော်လည်း protocol တစ်ခုလုံးတွင် သက်ရောက်မှု အကြီးမားဆုံးသော ဒီဇိုင်းဆုံးဖြတ်ချက် ဖြစ်သည်။

**လုပ်ဆောင်ချက်အသစ်တစ်ခု (capability) ထည့်သွင်းရန် protocol version အသစ် ထုတ်လုပ်ရန် မလိုအပ်ပါ။** TLV အသစ်တစ်ခု သတ်မှတ်လိုက်ရုံသာ ဖြစ်သည်။ Router အဟောင်းများက ၎င်းကို လျစ်လျူရှုထားမည်ဖြစ်ပြီး router အသစ်များက အသုံးပြုမည်ဖြစ်ရာ ကွန်ရက်ကြီးတစ်ခုလုံး အပြောင်းအလဲကာလအတွင်း မပြတ်တောက်ဘဲ ဆက်လက်လည်ပတ်နေနိုင်သည်။

ထို့ကြောင့်ပင် -

- **IPv6 support** ကို TLV အသစ်တစ်ခုအဖြစ် အလွယ်တကူ ထည့်သွင်းနိုင်ခဲ့သည်။ OSPF မှာမူ OSPFv3 ဟူသော protocol အသစ်တစ်ခုလုံးကို ဖန်တီးခဲ့ရသည်။
- **Segment routing** သည် IS-IS ပေါ်သို့ အရင်ဆုံးနှင့် အဆင်ပြေဆုံး ရောက်ရှိလာခဲ့သည်။ SIDs များသည် TLVs များသာ ဖြစ်ကြသည်။
- **Traffic engineering (TE)** extension များသည်လည်း ဤနည်းလမ်းဖြင့်ပင် ရောက်ရှိလာခဲ့သည်။

အကယ်၍ သင်သည် segment routing ကို အသုံးပြုရန် စီစဉ်နေပါက ၎င်းသည် ဝါသနာအရ ရွေးချယ်မှု မဟုတ်ဘဲ IS-IS ကို အသုံးပြုရမည့် အစစ်အမှန် ခိုင်လုံသောအကြောင်းပြချက် ဖြစ်သည်။

## Adjacency နှင့် DIS

IS-IS သည် neighbours များကို ရှာဖွေရန် **hello PDUs** များကို အသုံးပြုပြီး OSPF ထက် ပိုမိုတင်းကျပ်သော အချက်တစ်ခု ရှိသည်- L1 adjacency တည်ဆောက်ရန် **area IDs များ ထပ်တူညီရမည်**ဖြစ်ပြီး L2 adjacency မှာမူ area မတူညီသော်လည်း တည်ဆောက်နိုင်သည်။

LAN တစ်ခုပေါ်တွင် IS-IS သည် **DIS** (Designated Intermediate System) ကို ရွေးကောက်တင်မြှောက်သည် — OSPF ၏ DR နှင့် သဘောတရားချင်း တူညီသော်လည်း သိထားသင့်သည့် အရေးကြီးသော ကွာခြားချက် ၂ ခု ရှိသည် -

- **Backup DIS မရှိပါ။** DIS ပျက်စီးသွားပါက ရွေးကောက်ပွဲအသစ်ကို ချက်ချင်း ပြန်လည်လုပ်ဆောင်သည်။ IS-IS ရွေးကောက်ပွဲများသည် အလွန်လျင်မြန်သဖြင့် standby တစ်ခု ထားရှိရန် မလိုအပ်ဟု ယူဆထားကြသည်။
- **DIS ကို အစားထိုး သိမ်းပိုက်နိုင်သည် (pre-empted)။** ဦးစားပေး priority ပိုမိုမြင့်မားသော router တစ်ခု နောက်မှ ရောက်ရှိလာပါက DIS ရာထူးကို *ချက်ချင်း လွှဲပြောင်းရယူသည်*။ OSPF ၏ DR ကမူ ကွန်ရက် မတည်မငြိမ် မဖြစ်စေရန် ရာထူးကို တမင် ဆက်လက်ထိန်းသိမ်းထားလေ့ရှိသည်။

Flooding ပြုလုပ်သော ယူနစ်များသည် **LSPs** (Link State PDUs) များဖြစ်ကြပြီး OSPF ၏ LSAs နှင့် တိုက်ရိုက် သဘောတရားတူညီသည် — ထို့ပြင် OSPF ၏ LSA အမျိုးအစားများစွာနှင့် မတူဘဲ IS-IS တွင် ထို router ကြေညာလိုသမျှ အရာအားလုံးကို LSP တစ်ခုတည်းအတွင်း TLVs များအဖြစ် ထည့်သွင်းသယ်ဆောင်သွားသည်။

## Route Leaking နှင့် ATT Bit

မူလ default အခြေအနေအရ L1 router တစ်ခုသည် မိမိ area အကြောင်းကိုသာ သိရှိသည်။ ပြင်ပရှိ အရာအားလုံးဆီသို့ သွားရောက်ရန်အတွက် အနီးဆုံး L1/L2 router ဆီသို့ default route အတိုင်း သွားရသည် — အဆိုပါ L1/L2 router က ၎င်း၏ L1 LSP ထဲတွင် **ATT (attached) bit** ကို သတ်မှတ်၍ မိမိကိုယ်ကို ထွက်ပေါက်အဖြစ် ကြေညာထားခြင်း ဖြစ်သည်။

၎င်းသည် သက်သာလွယ်ကူပြီး အများအားဖြင့် ကောင်းမွန်ပါသည်။ သို့သော် ၎င်းသည် **အနီးဆုံးထွက်ပေါက်ကိုသာ ရွေးချယ်ခြင်း (nearest-exit routing)** ဖြစ်ပြီး အနီးဆုံးသည် အမြဲတမ်း အကောင်းဆုံး မဟုတ်နိုင်ပါ — အကယ်၍ အမှန်တကယ် သွားလိုသော destination သည် *အခြားသော* L1/L2 router ၏ နောက်ကွယ်တွင် ရှိနေပါက traffic သည် အနီးဆုံး ထွက်ပေါက်ဆီ အရင်သွားပြီးမှ ထိုမှတစ်ဆင့် L2 backbone ကို ပြန်လည်ဖြတ်သန်းကာ သွားရမည် ဖြစ်သည်။ ၎င်းသည် လမ်းကြောင်းမမှန်ဘဲ အလွန်အမင်း ဝေးကွာသွားစေနိုင်သည်။

**Route leaking** က ဤပြဿနာကို ဖြေရှင်းပေးသည်။ L1/L2 router တစ်ခုသည် သတ်မှတ်ထားသော L2 prefixes များကို L1 ထဲသို့ leak ပြုလုပ် (ယိုစိမ့်ထည့်သွင်း) ပေးနိုင်သောကြောင့် L1 router များသည် default route တစ်ခုတည်းကိုသာ မဟုတ်ဘဲ အစစ်အမှန် destination များကို မြင်တွေ့ရပြီး အမှန်ကန်ဆုံး ထွက်ပေါက်ကို တိုက်ရိုက် ရွေးချယ်နိုင်မည် ဖြစ်သည်။

လိုအပ်သော routes များကိုသာ ရွေးချယ်၍ leak ပြုလုပ်ပါ။ အရာအားလုံးကို leak လုပ်ပါက level ခွဲခြားထားခြင်း၏ မူလရည်ရွယ်ချက် ပျက်စီးသွားမည်ဖြစ်သည် — အဓိကအချက်မှာ ထွက်ပေါက်ရွေးချယ်မှု အမှန်တကယ် အရေးပါသော prefixes များကိုသာ leak လုပ်ပြီး ကျန်အရာများကို default route အတိုင်း ထားရှိရန် ဖြစ်သည်။

!!! note "OSPF နှင့် တူညီသော သဘောတရား"
    ၎င်းသည် OSPF ၏ stub areas များနှင့် အပေးအယူချင်း အတူတူပင်ဖြစ်သော်လည်း ဆန့်ကျင်ဘက်ဘက်မှ ချဉ်းကပ်ထားခြင်း ဖြစ်သည်။ OSPF areas များသည် မူလကတည်းက standard အပြည့်အစုံဖြစ်ပြီး အသေးစိတ်ကို လျှော့ချရန်အတွက် *opt into* လုပ်ရသည်; IS-IS L1 areas များမှာမူ မူလကတည်းက အသေးစိတ် မပါရှိဘဲ leaking မှတစ်ဆင့် အသေးစိတ်ကို ထပ်မံရယူရန် *opt into* လုပ်ရခြင်း ဖြစ်သည်။

## Overload Bit

Router တစ်ခုသည် ၎င်း၏ LSP ထဲတွင် **overload bit** ကို သတ်မှတ်ကာ အောက်ပါအတိုင်း ကြေညာနိုင်သည် — *ငါ့ဆီကို ရောက်နိုင်တယ်၊ ဒါပေမယ့် ငါ့ကိုဖြတ်ပြီး တခြားနေရာကိုသွားမယ့် transit traffic တွေကို ငါ့ဆီ မပို့ပါနဲ့။* အခြား router များသည် ထို router နှင့် တိုက်ရိုက်ချိတ်ဆက်ထားသော destination များဆီသို့ ဆက်လက်သွားနိုင်သော်လည်း အခြားနေရာများဆီသို့ သွားရန်အတွက်မူ ၎င်းကို လမ်းကြောင်းအဖြစ် အသုံးမပြုတော့ပေ။

အသုံးပြုသင့်သည့် အခြေအနေ ၂ ခုမှာ -

**စက်စတင်တက်ချိန်တွင် အလိုအလျောက် သတ်မှတ်ခြင်း (Automatically at boot)။** IGP converge ဖြစ်သွားသော်လည်း BGP table များ အပြည့်အဝ တက်မလာသေးသော router တစ်ခုသည် transit traffic များကို ဆွဲဆောင်မိပါက ၎င်းအနေဖြင့် forward မလုပ်နိုင်သေးသဖြင့် traffic များ မိနစ်ပေါင်းများစွာ ပျောက်ဆုံးသွားမည့် black hole ဖြစ်ပေါ်စေသည်။ ထို့ကြောင့် စက်စတင်ဖွင့်ချိန်တွင် BGP အပြည့်အဝ converge မဖြစ်မချင်း overload bit ကို သတ်မှတ်ထားခြင်းသည် full BGP tables များ ကိုင်တွယ်သော router တိုင်းအတွက် စံလုပ်ထုံးလုပ်နည်း ဖြစ်သည်။

**ပြုပြင်ထိန်းသိမ်းမှု ပြုလုပ်ရန် Manual သတ်မှတ်ခြင်း (Manually for maintenance)။** Overload bit ကို သတ်မှတ်လိုက်ပါ၊ traffic များ အခြားလမ်းကြောင်းများဆီသို့ ညင်သာစွာ ပြောင်းရွှေ့သွားသည်အထိ စောင့်ဆိုင်းပါ၊ ထို့နောက် စက်ကို စိတ်အေးချမ်းသာစွာ ပြုပြင်ပါ။ Interface များကို shut ချလိုက်ခြင်းဖြင့် ရုတ်တရက်ပြတ်တောက် reconverge ဖြစ်စေမည့်အစား ဤနည်းလမ်းက များစွာ ပိုမိုသန့်ရှင်းကောင်းမွန်ပါသည်။

!!! tip "အင်တာဗျူး မေးမြန်းသူများ အလွန်သဘောကျသော မေးခွန်း"
    ၎င်းသည် ကွန်ရက်တစ်ခုကို လက်တွေ့ run ဖူးသူများနှင့် configure ရုံသာ လုပ်ဖူးသူများကို ရှင်းရှင်းလင်းလင်း ခွဲခြားပေးနိုင်သော မေးခွန်းကောင်းတစ်ခု ဖြစ်သည်။ အထူးသဖြင့် စက် reboot ပြုလုပ်ပြီးနောက် အဘယ်ကြောင့် traffic black-hole ဖြစ်ရသည်ကို စဉ်းစားကြုံတွေ့ဖူးမှသာ BGP-convergence အခြေအနေကို နားလည်နိုင်မည် ဖြစ်သည်။

## Metrics: Narrow Default သတိပြုရန်နှင့် Metric 10 ထောင်ချောက်

IS-IS metric ကိုင်တွယ်ပုံသည် **Service Provider နှင့် Hyperscale network engineering အင်တာဗျူးများတွင် အရေးအကြီးဆုံး ခေါင်းစဉ်တစ်ခု ဖြစ်သည်** -

### ၁။ Default Metric 10 ထောင်ချောက် (The Default Metric 10 Trap)
Bandwidth ပေါ်မူတည်၍ cost ကို တွက်ချက်ပေးသော OSPF (`auto-cost reference-bandwidth`) နှင့် မတူဘဲ **IS-IS သည် bandwidth မည်မျှပင်ဖြစ်စေ INTERFACE တိုင်းအတွက် default metric 10 ကို သတ်မှတ်ပေးပါသည်!**
- **10 Mbps link**၊ **10 Gbps link** နှင့် **400 Gbps link** အားလုံးသည် default အားဖြင့် metric `10` ချည်းသာ ရရှိကြသည်!
- Metric များကို ကိုယ်တိုင် ပြင်ဆင်သတ်မှတ်ခြင်း သို့မဟုတ် wide metric အသုံးမပြုပါက IS-IS သည် 1G link နှင့် 400G link ပေါ်တွင် traffic ကို တူညီစွာ load-balance (ECMP) လုပ်မိပြီး ဆိုးရွားသော network ပြည့်ကျပ်မှု (congestion) ကို ဖြစ်ပေါ်စေပါလိမ့်မည်!

### ၂။ Narrow Metrics နှင့် Wide Metrics နှိုင်းယှဉ်ချက် (RFC 5305)

| Metric စတိုင် | RFC စံနှုန်း | Interface Metric Bits | အမြင့်ဆုံး Link Metric | Path Metric Bits | အမြင့်ဆုံး Path Metric | လုပ်ဆောင်နိုင်စွမ်းများနှင့် အသုံးချမှု |
|---|---|---|---|---|---|---|
| **Narrow Metrics** | RFC 1195 | 6 bits | **63** | 10 bits | **1,023** | ခေတ်ဟောင်း ကွန်ရက်များ၊ TE/SR sub-TLVs များအတွက် နေရာမရှိပါ |
| **Wide Metrics** | RFC 5305 | 24 bits | **16,777,215** | 32 bits | **4,294,967,295** | **ခေတ်သစ်စံနှုန်း၊ Segment Routing နှင့် SR-TE အတွက် မဖြစ်မနေ လိုအပ်သည်** |

```eos
router isis CORE
   metric-style wide
```

!!! warning "မလိုအပ်မီကတည်းက Wide Metrics ကို ကြိုတင်သတ်မှတ်ထားပါ"
    Domain တစ်ခုတည်းတွင် narrow နှင့် wide metrics များကို ရောနှောအသုံးပြုခြင်းသည် router များအကြား path cost အချက်အလက် ကွဲလွဲစေပါသည် — ထိုအခါ router များသည် မတူညီသော shortest-path tree များကို တွက်ချက်မိကြပြီး link-state protocol တွင် loop ဖြစ်ပေါ်စေသည့် အကြောင်းရင်း ဖြစ်လာသည်။

    ထို့အပြင် Wide metrics သည် **segment routing (SR-MPLS / SR-TE) အတွက် မဖြစ်မနေလိုအပ်သော ကြိုတင်သတ်မှတ်ချက် (prerequisite)** ဖြစ်သည်၊ အကြောင်းမှာ ထို extension များသည် narrow metrics တွင် နေရာမဆန့်သော sub-TLVs (Sub-TLV 22) များကို သယ်ဆောင်ရသောကြောင့် ဖြစ်သည်။ စတင် configure လုပ်သည့် ပထမဆုံးနေ့ကတည်းက ၎င်းကို ထည့်သွင်းသတ်မှတ်ပါ။

## Dual-Stack: Single နှင့် Multi-Topology နှိုင်းယှဉ်ချက်

IPv6 သည် TLV အဖြစ် ရောက်ရှိလာသောကြောင့် IS-IS instance တစ်ခုတည်းဖြင့် IPv4 နှင့် IPv6 နှစ်မျိုးစလုံးကို တပြိုင်နက် သယ်ဆောင်နိုင်သည်။ ထိုသို့ လုပ်ဆောင်ရာတွင် နည်းလမ်း ၂ သွယ်ရှိပြီး မှားယွင်းစွာ ရွေးချယ်ပါက သိမ်မွေ့သော ပြဿနာများကို ဖြစ်ပေါ်စေနိုင်သည် -

**Single topology** — SPF တွက်ချက်မှုတစ်ခုတည်း၊ လမ်းကြောင်းတစ်ခုတည်းသာရှိပြီး address families နှစ်ခုစလုံးက ထိုလမ်းကြောင်းအတိုင်း လိုက်သွားသည်။ ရိုးရှင်းပြီး ထိရောက်မှုရှိသော်လည်း **link တိုင်းတွင် protocol နှစ်မျိုးစလုံး ရှိနေရမည်** ဟု ယူဆထားသည်။ IPv4 သာရှိသော link တစ်ခုကို IPv6 အတွက်ပါ ဆက်လက်အသုံးပြုနေမည်ဖြစ်ရာ ထို IPv6 traffic များ black-hole ဖြစ်သွားပါလိမ့်မည်။

**Multi-topology (MT)** — Address family တစ်ခုစီအတွက် သီးခြား SPF တွက်ချက်မှု ပြုလုပ်သည်၊ ထို့ကြောင့် တစ်စိတ်တစ်ပိုင်းသာ စတင်ဖြန့်ကျက်ထားသော ကွန်ရက်တွင် IPv4 နှင့် IPv6 တို့သည် သီးခြားလမ်းကြောင်းများအတိုင်း မှန်ကန်စွာ သွားလာနိုင်သည်။

```
router isis CORE
 net 49.0001.0000.0000.0001.00
 metric-style wide
 !
 address-family ipv6 unicast
  multi-topology
```

သင်၏ dual-stack စနစ်သည် links အားလုံးပေါ်တွင် အမှန်တကယ် ပြည့်စုံပြီးသားဖြစ်မှသာ single topology ကို အသုံးပြုပါ။ သို့မဟုတ်ပါက Multi-Topology (MT) သည် အလုံခြုံဆုံး ရွေးချယ်မှု ဖြစ်သည်။

မည်သို့ပင်ဖြစ်စေ ဤသည်မှာ **protocol instance တစ်ခုတည်းသာ** ဖြစ်သည် — Dual-stack အတွက် v2 နှင့် v3 ဟူသော database နှစ်ခုပါသည့် သီးခြား protocol နှစ်ခုကို run ရသော OSPF နှင့် ကွာခြားသည့် အချက်ဖြစ်သည်။

## အင်တာဗျူး မေးခွန်းများ (Interview questions)

??? question "Provider များသည် Backbone တွင် OSPF ထက် IS-IS ကို အဘယ်ကြောင့် ပိုမိုနှစ်သက်ကြသနည်း။"
    ပေါင်းစပ်ထားသော ခိုင်လုံသည့် အကြောင်းရင်း ၃ ချက် ရှိပါသည်။ ပထမအချက်မှာ Layer 2 ပေါ်တွင် တိုက်ရိုက် run သောကြောင့် network ပြင်ပမှ လှမ်းတိုက်ခိုက်၍ မရနိုင်ခြင်း။ ဒုတိယအချက်မှာ TLV encoding ကြောင့် စွမ်းဆောင်ရည်အသစ်များ (IPv6, segment routing, TE) ကို protocol တစ်ခုလုံး ပြန်လည်မရေးသားရဘဲ extension အဖြစ် အလွယ်တကူ ထည့်သွင်းနိုင်ခြင်း။ တတိယအချက်မှာ L2 backbone သည် သတ်မှတ်ထားသော area အစား ချိတ်ဆက်နေသော routers ကွင်းဆက်ဖြစ်သဖြင့် ကွန်ရက်ချဲ့ထွင်ခြင်း သို့မဟုတ် ပေါင်းစည်းခြင်းများတွင် အနှောင့်အယှက် အနည်းဆုံး ဖြစ်စေခြင်းတို့ ဖြစ်သည်။

??? question "NET ဆိုသည်မှာ အဘယ်နည်း၊ မည်သည့်အစိတ်အပိုင်းက Router ကို အမှန်တကယ် ဖော်ပြသနည်း။"
    Network Entity Title ဖြစ်ပြီး OSI-style address တစ်ခု ဖြစ်သည်။ အလယ်တွင်ရှိသော 6-byte အရွယ်အစား **system ID** သည် router ကို သီးသန့်ဖော်ပြပြီး domain တစ်ခုလုံးတွင် ထူးခြားရပါမည်။ ၎င်း၏ အရှေ့တွင် Area ID ရှိပြီး အနောက်ဆုံးရှိ NSEL သည် router အတွက် အမြဲတမ်း `00` ဖြစ်သည်။

??? question "IS-IS ၏ Area သတ်မှတ်ချက်သည် OSPF နှင့် မည်သို့ ကွဲပြားသနည်း။"
    IS-IS သည် **Router တစ်ခုလုံးကို** area ထဲသို့ ထည့်သွင်းသတ်မှတ်ပြီး OSPF သည် **Interface တစ်ခုစီအလိုက်** သတ်မှတ်သည်။ ထို့ကြောင့် IS-IS router တစ်ခုသည် OSPF ABR ကဲ့သို့ area နှစ်ခုကို ခွ၍ မရပ်တည်နိုင်ပါ — ထိုသို့သော တူညီသည့် အခန်းကဏ္ဍမှာ L1 နှင့် L2 နှစ်ခုစလုံးကို တပြိုင်နက် run ထားသော router ဖြစ်သည်။

??? question "Metric-style wide သည် ဂဏန်းပမာဏ ပိုမိုကြီးမားလာခြင်းအပြင် အဘယ်ကြောင့် အရေးပါသနည်း။"
    Narrow metrics သည် link တစ်ခုလျှင် အများဆုံး 63 သာ သတ်မှတ်နိုင်သဖြင့် ခေတ်သစ် bandwidth ကွာခြားချက်များကို မဖော်ပြနိုင်တော့ပါ။ ထို့ထက် ပိုမိုအရေးကြီးသည်မှာ Wide metrics များကို အပိုဆောင်း အချက်အလက်များ ထည့်သွင်းနိုင်သော TLVs များဖြင့် သယ်ဆောင်ထားသဖြင့် **Segment Routing နှင့် Traffic Engineering တို့အတွက် မဖြစ်မနေ လိုအပ်သော အခြေခံအချက်** ဖြစ်လာခြင်း ဖြစ်သည်။ ထို့အပြင် Metric စတိုင်များ ရောနှောခြင်းသည် router များအကြား cost မကိုက်ညီမှုများကို ဖြစ်ပေါ်စေသည်။

??? question "Single-topology dual-stack ကို မည်သည့်အချိန်တွင် မရွေးချယ်သင့်သနည်း။"
    Link တိုင်းပေါ်တွင် IPv4 နှင့် IPv6 နှစ်မျိုးစလုံး မရှိသေးသည့် အခြေအနေတိုင်းတွင် ဖြစ်သည်။ Single topology သည် နှစ်မျိုးစလုံးအတွက် tree တစ်ခုတည်းကိုသာ တွက်ချက်သဖြင့် IPv6 traffic သည် IPv4 သာရှိသော link ပေါ်သို့ ရောက်ရှိသွားကာ black-hole ဖြစ်သွားနိုင်သည်။ Multi-topology ကမူ family တစ်ခုစီအတွက် သီးခြား tree တွက်ချက်သဖြင့် ထိုပြဿနာကို ရှောင်ရှားနိုင်သည်။
